# Reflection

I drew the lines by asking what each tool is allowed to decide. `find_open_slots` decides nothing and changes nothing; it reports one day. `send_email` changes the world but decides nothing either: it sends exactly the text it is given. `offer_scoping_slots` owns the decisions (which days to search, which slot to keep from each day, what the offer says) and uses the other two to carry them out. My first orchestration design, `book_earliest_scoping_call`, failed this test: it took the same inputs as the action tool and ended in the same effect, so for "book me a call" the model could not tell them apart. I also asked whether the orchestration tool should exist at all, since the agent could call `find_open_slots` and then `send_email` itself. I kept it because the search can take up to ten lookups, which would be up to ten model round trips, and in code the model cannot email a time it never checked. Chapter 5 describes orchestration as agents serving as tools for other agents; mine is plain code, because this coordination needs no judgment that a fixed rule cannot make.

Three tools felt right for this slice of the front desk: in the live run every request reached the right tool on the first try, which I credit to the tools not overlapping rather than to there being few of them. Keeping the service catalogue as a resource, not a fourth tool, also left the prices under the host's control. The run also showed what is missing. An offer does not hold its slots, so the next tool would be `hold_slot`, which changes the calendar rather than the inbox and so would not overlap with `send_email`. The duplicate guard blocked a legitimate "please resend", so it needs a time window or an explicit resend flag. Finally, I would swap the outbox and the JSON calendar for SMTP and a real calendar API behind the same interfaces, and serve the toolkit over HTTP so other agents can share it.
